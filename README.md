# dsh-jm

发 `jm350234`，那本漫画就躺到桌面了 —— 一张一张按 `001.jpg 002.jpg 003.jpg` 排好。

给 **DeepSeek Harness** 用的插件。**自带 Python 依赖**，装完不用 pip 装任何东西。

## ⚠️ 分发前必须知道的三件事

### 1. vendor 里的 .pyd 绑死 Python 3.12

```
_cffi_backend.cp312-win_amd64.pyd
Crypto/Cipher/_raw_aesni.pyd  （cp312）
```

这些是按 3.12 编译的二进制扩展。DSH 桌面版自带 3.12，正常没问题。
但如果对方是 3.13 或别的版本，Windows 直接报 ImportError: DLL load failed ——
这错误看起来像插件坏了，其实是版本不匹配。

`安装.bat` 里加了版本检查，会提前说。真要跨版本用，让对方自己重建：

```bash
python -m pip install jmcomic pillow pycryptodome curl_cffi pyyaml urllib3 --target vendor
```

### 2. 只有 Windows

package.json 里写了 os: [win32]。安装.bat、注册表读桌面路径、%TEMP% 缓存目录
全是 Windows 的东西，macOS / Linux 跑不起来。

### 3. 首次运行会重探域名

别人第一次用会比你慢 10~30 秒：探活 API 域名和图片 CDN 各一轮。
结果缓存 5 分钟，之后就快了。不用当成插件卡住。

## 设置 → JM 个性化

设置面板里新增一页，三个输入框，配置存在 `~/.dsh/plugin-data/dsh-jm/prefs.json`：

**① 漫画库文件夹** —— 填一个目录，点「分析这个目录」，就在**那个目录里**生成 `个性化分析.md`。

分析只读不改：只写那一个 md，不动任何图片。报告里给的是

- 共几本 / 几页 / 多大
- 平均页数 → 判断你偏短篇还是单行本
- 页数分档：≤30 / 31~80 / >80
- 主流分辨率（分辨「手机版收藏」和「高清收藏」）
- 格式分布
- 逐本清单（页数 / 大小 / 分辨率）

尺寸只**抽 3 张**看：一本 200 页全解码要等半天，而同一本的图几乎必然同尺寸。

**② 精选文件夹** —— 自己新建一个目录，把**你觉得好的、高潮的那几页**复制进去。

这段是画风推荐的真正依据。全库平均只能说明「你收藏了什么」，
精选目录才是「你真正喜欢什么」—— 两者常常不一样（比如库里 70% 是短篇，
但你真正喜欢的是那几张特定构图）。报告会给出两者的差距：

- 距离 < 1.0：高度一致，你挑的和收藏的口味统一
- 1.0 ~ 2.5：略有偏差，精选更偏个人偏好
- \> 2.5：偏差明显，收藏里有很多其实你不是最喜欢的

**③ 已下载 / 看过的漫画** —— 大文本框，随便粘。解析不按行，直接全文抓 5~8 位数字，
所以 `jm1445283, 1489503`、`123 456 789`、`[某某] 某本 1445283` 都能吃。

### 分析报告里有三段

**1. 标签偏好** —— 每个 tag 命中多少本。统计的是**本数**不是出现次数，
否则标签写得全的本子会主导排名，结论会变成「你喜欢标签写得全的作者」。

标签从哪来：下载时自动在同目录写 `标签.txt`，分析时直接扫盘，零网络。
格式是 `jm: / title: / author: / pages: / tags: 蘿莉, 中出, 中文`。

**2. 画风画像** —— 五个可比的数值指标：

| 指标 | 含义 |
| --- | --- |
| 饱和度 | 0=黑白，0.4+=浓彩 |
| 亮度 | 越低越暗调 |
| 对比度 | 高=硬光硬影 |
| 线密度 | 高=线条繁复 |
| 肤色占比 | 高=肉体特写多 |
| 暖色倾向 | 正=偏粉橙，负=偏蓝青 |

⚠️ **采样规则：跳过首 3 页和尾 3 页，中间等距取 8 张，每指标取中位数。**

为什么跳过首尾：第一页常是封面、最后一页常是广告 / 汉化组招募 / 版权页。
实测第一本「子宮脫手淫直播」首尾抓到的 sat=0.000、gray=180 —— 那是白底黑字，
根本不是漫画内容，拿它算画风，算出来的是「这个作者喜欢留白」。

为什么取中位数不是平均：广告页、跨页大图、纯黑页都是离群值，平均会被拽跑。

还有第二道防线：算完发现 `sat<0.04 且 edge<0.03` 的页（白底/纯色底）直接丢弃。

**3. 精选画风** —— 见上面的②。

### 元数据规格（标签.txt）

每本下完后在同目录写一份 `标签.txt`，这是整个个性化的地基：

```
jm: 1487216
title: [羊咩咩] 鈴蘭的催眠調教
author: 羊咩咩
pages: 41
dims: 800x1169
tags: 獸耳, 蘿莉, 催眠, AI繪圖, 中文
size_mb: 15.9
analyzed:
downloaded: 2026-11-15 00:12
```

`analyzed` 是**防重复统计**的开关：空 = 还没纳入过，有值 = 已算过。
重下同一本时会**保留原值**（否则标记被冲空，下次又算一遍，权重翻倍）。

补全工具：`complete` 命令扫一个目录，缺什么补什么。
没有 jm 号的会按「索引 → 作者维度搜 → 标题搜」三级匹配后回写索引。

### 个性化推荐

`recommend` 输出 `喜欢的漫画/个性化推荐.md`，打分是三部分：

| 项 | 权重 | 怎么算 |
| --- | --- | --- |
| 标签分 | 0.6 | 候选 tag 与你的标签榜按权重加权重合 |
| 画风分 | 0.35 | 候选项**封面**与精选基准的距离（3.0 归一） |
| 新本分 | 0.05 | 近 90 天发布的小额加分 |

三个分值都原样写进报告 —— 必须能看出「为什么这一本排第一」，否则就是随机数生成器。

⚠️ 画风分只能拿**封面**比（候选项还没下载），而封面和正文画风可能不同。这一点写在报告里。

### 精选截图目录的约定

```
精选截图/
  ├─ 还没分析的/    ← 你往这里扔图
  └─ 已经分析的/    ← 分析完自动挪过来，外加一份 画风档案.json
```

**为什么必须挪走**：精选目录是画风基准。分析过的图留在原地，下次又算一遍，
基准被自己污染，权重翻倍。物理挪走比记文件名可靠 —— 改个名就废了的方案不算方案。

### 接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/dsh-jm/prefs` | 读配置 |
| POST | `/dsh-jm/prefs` | 写配置（body: `{patch:{...}}`） |
| POST | `/dsh-jm/analyze` | 扫目录并写报告（body: `{path}`） |

⚠️ 这三个接口能读用户磁盘，所以只允许同源：校验 `sec-fetch-site` 与 `Origin/Host` 一致，
跨站直接 403。设置页本身是 `client.js`，纯 JS 手写 `h(...)`，没有构建步骤。

**落盘位置**：真实桌面（读注册表拿的，不是硬拼 `~/Desktop`）
`/<本子名>/001.jpg 002.jpg …`

多话的书会合并成一个文件夹、一条连续编号。
比如《董卓 上+下》两话各 25 页 → 一个文件夹，`001.jpg` 一路到 `050.jpg`。

### 查作者的其他作品

`jm_author` 给一个 jm 号（**可以不给**，不给就用最近下载的那本），返回：

- 作者名（`author`），当前这本的标题
- 这个作者名下全部作品：`id / title / date`，当前这本带 `"current": true`
- `count` 是筛完之后真正属于他的本数，`total` 是站点的模糊命中数

⚠️ 两个必须在代码里挡住的事：

1. **`search_author` 是模糊搜索。** 搜「びよびよ」会把「ひよひよ」「ピヨピヨ帝國」
   「ひよひよくらぶ」全捞回来，站点报的 `total` 是模糊命中数。
   驱动会拿每条结果的 `author` 字段做归一化比较（小写、去括号、去空白），
   只留真正同名的。所以 `count` 会明显小于 `total`，这是对的。
2. **`page.content` 的元素是 tuple** `(album_id, {name, adddate, author, ...})`，
   跟 `episode_list` / `search_site` 同一个毛病，按对象 getattr 读只会拿到空。

多人合作时只按第一个名字搜，返回里的 `note` 会说明可能漏掉合著的。

### 把一个作者的全下下来

`jm_author_download` 按「作者 → 作者名下全部作品」整批下，落成两层：

```
桌面/びよびよ/
  ├─ [びよびよ] 性快感墮落/001.jpg 002.jpg …
  ├─ [びよびよ] 芒果味小孩/001.jpg …
  └─ …
```

几个刻意的取舍：

- **已经下过的跳过。** 判据是目标目录里有没有图。重跑一次 = 补下失败的那几本，不会把 33 本再下一遍。
- **一本失败不影响后面。** 失败的收进 `failed`，返回里一起给，调用方决定要不要补跑。
- **探活结果缓存 5 分钟。** 每本都探一次 API 域名 + 图片 CDN 要多花 6~12 秒，33 本就是好几分钟，
  而且 CDN 几十秒就变、探完就过期。缓存只用来避免重复探同一件事。
- 默认按日期倒序（新的先下），传 `order=old` 反过来。
- **缺页算失败。** `download_album(check_exception=False)` 会把「某张图重试全挂」降级成一条日志就放过，
  一本 32 页能交出 21 页还报 ok。现在用 `album.page_count` 对账，缺了就抛、换线路重试。

### 按 tag 挑：先看封面，再决定下哪本

两步，中间隔一次人眼：

1. `jm_pick` —— 按 tag 搜前 N 本，把**封面**下到桌面并编号
2. 你看图，说「第 3 个」或「3,7,9」
3. `jm_pick_download` —— 只下挑中的那几本

```
桌面/jm挑选/巨乳/latest-all/
  ├─ 01.jpg  02.jpg  …  （封面，编号即序号）
  ├─ 索引.txt   （给人看：编号 / jm号 / 标题 / 作者 / 日期）
  └─ 索引.json  （给机器读：编号 → jm 号的对照表）
```

排序 `order`：`latest`（最新）/ `views`（最多浏览）/ `likes`（最多喜欢）/ `score` / `comments` / `pictures`。
时间 `time`：`all` / `today` / `week` / `month`。

⚠️ 三个坑（都写在代码注释里了）：

- **排序是拼出来的。** 站点的 `o` 收 `{order}_{time}`，比如本月最多浏览 = `mv_m`；全时段是裸 `mv`。
  jmcomic 的 `search_site` 内部才拼，驱动直接用 `search()`，所以 time 必须自己拼，
  否则「本月最热」会悄悄退化成「全时段最热」。
- **编号必须和索引一起写。** 只有图没有号，用户说「我要第 5 个」就只能靠文件名猜；
  而 `01` 和 `1` 在资源管理器里排出来的顺序不一样，迟早对错。
- **封面单张挂了不整批重来。** 一张失败换个线路再试一次，还失败就标「缺图」，不影响挑。

### 画质：默认就是无损（2026-11 改的）

这里以前有个真 bug，值得留档：

1. jmcomic 解打乱后存图走 `JmImageTool.save_image` → 原生 `image.save(path)`，
   存 `.webp` 时用的是 PIL 默认 **quality=80 有损**。
2. 我这边 `number_into` 又把它 `convert("RGB").save("JPEG", quality=95)` 了一道。

两道压缩叠起来，1439×2047 的原图细节（网点、细线、拟声字）肉眼可见地糊。

现在两处都改掉了：

- 存图打补丁：webp 用 `lossless=True, quality=100, method=0`，png/gif/bmp 走原生无损，
  jpg（有损格式没办法）用 `quality=100, subsampling=0` 顶到极限。
- 重编号只改名，**不动字节**，扩展名跟着原图走（所以是 `001.webp` 不是 `001.jpg`）。

### 编码档位为什么是 0 不是 6

同一张 1680×2370 / 1621KB 正文页，`lossless=True, quality=100`：

| method | 耗时 | 体积 |
| --- | --- | --- |
| 0 | 0.46s | 1761KB（+8.7%） |
| 2 | 1.26s | 1626KB（+0.3%） |
| 4 | 1.75s | 1629KB（+0.5%） |
| 6 | 10.24s | 1621KB（+0.0%） |

四者**像素完全一致**，差的是编码器愿意花多久找更省的写法。
method=6 花 22 倍时间换 8.7% 体积 —— 而这个 8.7% 是 1.6MB→1.76MB 的量级，
相对一个本子几十上百 MB 可以忽略。之前用 6，1952 页的合集光编码就要 5 小时，
**这才是下载慢的真正主因**。

想换回更省的写法：环境变量 `DSH_JM_WEBP_METHOD=4`。
并发也从 4 提到了 8（webp 编码在 C 层释放 GIL，能真并行），实测 49 页 13.6 秒 ≈ 3.6 页/秒。

验证过：lossless webp 存出来再读，像素完全一致（`same pixels: True`）；
默认 q80 往返最大差值 21 —— 那就是以前丢掉的画质。

> 说明一句：站点上的 webp 本来就是有损压过的，我们没法让它变回原始。
> 「无损」指的是**不再额外损失**，不是凭空恢复。

### 批量下载的四个坑（2026-11-14 全部踩过并修掉）

1. **`ok` 的语义错了，用户看到的是「未知错误」。**
   以前 `cmd_pick_download` 写的是 `ok = not failed`，只要有一本失败就整批 `ok:false`，
   插件端 `runDriver` 看到 `ok:false` 就当整体失败抛出去 —— 而这里又没填 `error` 字段，
   于是聊天里出现一句「dsh-jm: 未知错误」，实际上 6 本已经躺在桌面上了。
   现在：全挂才 `ok:false` 并带上明细；部分失败用 `ok:true` + `partial:true`。

2. **简繁标题不一致，`skip_existing` 形同虚设。**
   `album?id=` 返回简体标题，下载接口拿到的 `album.name` 是繁体（「綾枷」vs「绫枷」），
   `safe_name` 之后是两个目录名，按标题找已下载目录永远找不到，每次重跑都重下一遍。
   现在桌面根目录有一张 `.dsh-jm-index.json`，用 **jm 号**做键记「下到哪个目录了、多少页」，
   绕开标题差异。索引命中时连网络都不发，7 本判定完只要 287ms。

3. **大合集本永远下不完。** 1489276「提瓦特人形譚 1-5」有 1952 页，
   按实测速度要 30 分钟以上，而单本超时封顶 900 秒 = 必掐断，掐断后从第 1 页重来。
   现在两件事一起改：`per_book_timeout` 上限提到 3600 秒；
   缓存目录从随机临时目录改成 `%TEMP%/dsh-jm-cache/<album_id>/` 并打开 `download.cache`，
   超时重跑只补缺的那几百页（实测续传有效，最终 1952/1952 下齐）。
   **缓存只在成功搬家之后才清**，中途失败留着给下次续传。

4. **半本被当成已下载。** 只判「目录在不在」是不够的，超时中断会留下半本。
   现在按 `album.page_count` 对账，页数不齐就重下。

### 大本先拦下来（max_pages，默认 60）

批量下载时，页数超过 `max_pages`（默认 60）的本子**先不下**，收进返回值的 `deferred`：

```json
{"deferred":[{"id":16779,"title":"ひよひよふぅーじんろく","pages":399,"reason":"399 页，超过 60 页上限"}]}
```

任务结束时由助手主动问用户要不要下，用户说要，再拿同样的 id 补：

```
jm_pick_download({ id: "16779,15487", max_pages: 0 })   // 0 = 不限
```

几个刻意的取舍：

- **顺序不能反。** 先下完再问等于把带宽和时间先花了，用户说不要就白费。
- **已下齐的不再提示。** 判断顺序是 skipped → deferred → 下载，不然每次跑都提示同一批，噪音消不掉。
- **问不到页数就不拦**（返回 0）。宁可多下一本，也不要因为一次接口抖动把用户要的东西藏起来。

## 它是怎么工作的

**走 APP API，不是网页。** 这点是被坑出来的：

最初我手写的是网页版驱动，在六个镜像上（`18comic.ink` / `jmcomic.me` / `18comic.vip` …
全部返回 `album_missing`，一度误判成"这本被下架了"。换成 `jmcomic` 库走 APP API 一问：
这本明明在，是《董卓 上+下》，2 话 50 页。
**网页镜像的数据是残缺的，APP API 才是全的。**

| 谁 | 干什么 |
| --- | --- |
| `vendor/jmcomic`（随插件打包） | 域名自动更新、请求签名、取详情、下载、**解打乱** |
| `lib/jm.py` | 下到临时目录 → 合并所有话 → 重编成 001…N |
| `index.js` | 注册工具、往系统提示塞触发词、找 Python |

### 解打乱是什么

站上每张图被拆成 2~20 条横带、上下倒序拼起来。段数 =
`md5(aid + 页码)` 末位字符码（`268850 ≤ aid ≤ 421925` 取模 10，否则模 8），
再查 `{0:2, 1:4, …, 9:20}`。不还原的话每张图都是错位的横条。

`jmcomic` 原生就带这个，不用自己写。
（我手写的那份留在 `lib/jm_handmade.py.bak`，是完整可用的对照实现。）

## 改代码前必看的三个坑

1. **必须下到临时目录再搬。**
   `jmcomic` 的 `DirRule` 在 `__init__` 里就把 `rule_dsl` 解析成 `parser_list` 了，
   **之后再改 `.rule_dsl` 字符串只改字段，解析表还是旧的**。
   所以没法让它"把所有话塞进一个文件夹"——默认的 `Bd_Pname` 会把
   《董卓 上+下》拆成 `董卓 上+下/` + `董卓 下/` 两个桌面文件夹，各 25 页。

2. **库的日志会毁掉 JSON 返回值。**
   `jmcomic` 不走 logging，直接 `print` 到 stdout（一本 50 页能刷 100+ 行）。
   驱动里先 `sys.stdout = sys.stderr`，再留一个 `real_stdout` 句柄写最终 JSON。
   否则 Node 端 `JSON.parse` 直接炸，报 `驱动输出不是 JSON（code=0）`，
   而其实下载全成功了。

3. **`episode_list` 的元素是三元组，不是对象。**
   `List[Tuple[str, str, str]]` = `(photo_id, photo_index, photo_name)`。
   按对象 `getattr(e, "title")` 去读，拿到的全是空串，章节名就一直是 `["", ""]`。

### 还有一个关于超时的

`jmcomic` 默认 `retry_times=5`，每次请求 30 秒超时 = 一次失败要挂 **150 秒**。
而 DSH 工具层有 **60 秒**死线，表现就是"工具超时"，真正原因全埋在日志里。
所以驱动把 `retry_times` 压到 2、请求超时压到 20 秒，最坏 ~60 秒内能给出明确结论。

## 排障

| 症状 | 原因 |
| --- | --- |
| `下载失败（...直连和代理都试过了）` | 网络抽风，过会儿再试；或者手动传 `proxy` 参数 |
| `驱动输出不是 JSON` | stdout 被库日志污染了，看 `main()` 里的重定向 |
| 图是横条错位的 | `aid`/`scramble_id` 解析问题 |
| 一本书变成好几个文件夹 | 没走临时目录合并，见坑 1 |
| 工具超时但日志显示成功 | 重试次数太多，见「关于超时」 |
| `缺少 jmcomic 依赖` | `vendor/` 丢了，重新装一份（见下） |

补依赖：

```bash
python -m pip install jmcomic --target "<插件目录>/vendor"
```

## 已知限制

- 只测过 Windows（`安装.bat`、注册表读桌面路径、注册表读代理都是 Windows 专属）
- 直连能用但不稳（`18comic.ink` 实测 10 次里 9 次通），抽风时会自动试本机代理
- 没做登录，只能下公开可见的本子
